# Audit BDD Nexytal Gestion - 2026-07-09

## Perimetre

Base analysee: dump `dbs15772578` fourni le 2026-07-09 et code local `api/` + `src/`.
Sites cibles: formation, recrutement, medical, carriere, trainers, coaching.

## Synthese

La base couvre globalement les 6 sites, mais le dump fourni n'est pas exploitable tel quel sur le long terme: plusieurs vues sont syntaxiquement corrompues, presque aucune contrainte relationnelle n'existe, des tables appelees par le projet sont absentes, et certains garde-fous de securite sont incomplets.

Correctifs fournis:

- `api/core/AdminSession.php`: les nouvelles sessions admin stockees dans `core_admin_sessions.id` ou `core_admin_sessions.token` sont maintenant hashees en SHA-256; compatibilite temporaire avec les anciennes lignes non hashees.
- `api/core/Audit.php`: suppression automatique des champs sensibles (`password`, `token`, `secret`, `session`, `authorization`) avant ecriture dans `core_audit_logs`.
- `api/sql/dbs15772578_hardening_2026_07_09.sql`: patch SQL de durcissement et coherence.

## Findings critiques

1. Vues SQL cassees dans le dump

Les vues exportees contiennent des fragments invalides (`GROUP BY c.id``id`, `IS NOT NULLnot null`, `r.status = 'actif''actif'`, aliases dupliques dans `v_gestion_candidatures`). Impact: import impossible ou vues inutilisables. Corrige dans le patch SQL avec `SQL SECURITY INVOKER` pour eviter la dependance au `DEFINER=o15772578@%`.

2. Sessions admin stockees en clair dans le chemin schema `id`

Le schema annonce `core_admin_sessions.id` comme SHA-256, mais le code inserait le token brut; la variante avec colonne `token` avait le meme risque. Impact: vol BDD = sessions reutilisables jusqu'a expiration. Corrige dans `AdminSession::create()`, validation compatible hash + legacy.

3. Audit pouvant journaliser des secrets

`Audit::log()` encodait directement `old_data/new_data`; quelques routes nettoyaient a la main, mais pas toutes. Impact: fuite durable de mots de passe/tokens dans les logs. Corrige par filtrage centralise recursif.

4. Tables appelees par le code mais absentes du dump

Manquants credibles: `gdpr_deletion_requests`, `recrutement_scoring_config`, `recrutement_scoring_history`, `blog_comments`, `blog_related_posts`, `blog_posts_versions`, `newsletter_campaigns`, `newsletter_events`, `marketing_email_logs`. Impact: endpoints/pages cassables selon activation. Ajoute dans le patch SQL.

## Findings majeurs

1. Peu de contraintes relationnelles

Le dump ne declare que deux FK (`trainers` -> `expertises`, `trainer_expertise_links`). Les tables multi-site et metier peuvent accumuler des orphelins. Le patch ajoute des index, mais les FK doivent etre ajoutees apres controle d'orphelins sur la base de production pour eviter un echec d'ALTER.

2. 2FA absente pour superadmin/admin

Le contexte demande la 2FA, mais le schema ne la portait pas. Le patch ajoute `two_factor_secret` et `two_factor_enabled`; il reste a brancher l'UI/API de verification TOTP.

3. CSRF non visible pour les mutations admin

L'API utilise des Bearer JWT; il n'y a pas de mecanisme CSRF visible pour les formulaires admin. Si le token reste en stockage navigateur accessible JS, le risque dominant est XSS; si cookie un jour, CSRF devient critique.

4. Rate limiting limite au login admin

`RateLimit` existe pour `/api/admin/login`, mais les reset password et portails recruteur/trainer/coaching doivent aussi etre limites par IP + compte.

5. RGPD incomplet

`rgpd_consent_at` est present sur les formulaires majeurs, mais purge/anonymisation et demandes de suppression necessitent `gdpr_deletion_requests` et une tache planifiee. Le patch ajoute la table, pas encore le job.

6. Uploads

Le projet a une couche upload, mais il faut confirmer en production: stockage hors racine web, allow-list extensions/MIME, taille max, noms aleatoires, scan antivirus si possible. Les champs `cv_filename`, `avatar_url`, `media_library` sont sensibles.

## Findings mineurs

1. Tables non referencees actuellement par le code

Aucune suppression automatique recommandee. Tables non referencees par `api/` + `src/` hors SQL: `candidat_tokens`, `coaching_client_profiles`, `coaching_coach_client_links`, `coaching_portal_tokens`, `coaching_session_bookings`, `demandes_urgentes`, `trainer_appointment_slots`, `trainer_client_links`, `trainer_client_profiles`, `trainer_portal_tokens`, `trainer_session_bookings`.

Decision: ne pas drop. Elles correspondent a des besoins explicites du contexte: portails candidats/coaches/trainers, demandes urgentes, reservations, sessions, notifications. Les supprimer casserait l'objectif long terme meme si certaines pages ne sont pas encore branchees.

2. Tables SQL absentes mais modules non enregistres

Certains modules existent mais ne sont pas inclus dans `api/index.php` (`blog/comments.php`, `newsletter_extended.php`, `email_logs.php`, `gdpr/deletion_requests.php`, `trainer/trainer_applications.php`, `recrutement/scoring_config.php`). Il faut soit les enregistrer, soit retirer les pages/API correspondantes. Le patch cree les tables pour eviter une base incomplete.

## Avant / apres

Avant:

- Vues du dump non fiables.
- Sessions admin `id` potentiellement token brut.
- Logs d'audit dependants du nettoyage manuel des routes.
- Tables metier manquantes pour GDPR, scoring, newsletters avancees, commentaires/versioning blog.
- Index multi-site insuffisants pour croissance.

Apres les changements locaux:

- Sessions admin hashees cote code.
- Audit central filtre les secrets.
- Script SQL idempotent de reparation disponible.
- Decision explicite: aucune table supprimee sans preuve de non-usage metier + validation donnees production.

1. Sauvegarde BDD production.

3. Appliquer `api/sql/dbs15772578_hardening_2026_07_09.sql` sur staging.
